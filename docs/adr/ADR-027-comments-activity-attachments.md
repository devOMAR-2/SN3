# ADR-027 — Comments, mentions, activity audit and attachments

- **Status:** Accepted
- **Date:** 2026-10-21
- **Task:** CORE-008 (#17)
- **Decision inputs:** BRD FR-COL-001, FR-COL-002, FR-COL-004 (mentions), FR-TASK-006, FR-TASK-007 (attachments, mentions), FR-PROJ-004/-005/-007, NFR-SEC-003, NFR-SEC-005, §7 role matrix, authorization test invariant; ARCHITECTURE.md §5.2, §5.3, §7, §11.2, §11.3, DECIDED-003, DECIDED-004, DECIDED-011; DATABASE.md §5, §10, §11, §12, §13, §16 (DB-T01, DB-T02, DB-T04, DB-T08, DB-T12, DB-T13), §19, §20; API_SPEC.md §1, §4, §6.1–§6.3, §9, §12, §13, §15, §17, §18; DEVELOPMENT_PLAN.md CORE-008 ("File access scoped; 25MB Cloud cap; upload abuse tests"); acceptance scenarios AUTH-02, AUTH-04, AUTH-05, LIM-01, LIM-02, DEL-02; AGENTS.md §6, §8; ADR-017, ADR-018, ADR-020, ADR-022, ADR-023, ADR-024

## Context

CORE-008 adds the collaboration layer on top of tasks (CORE-005): comments with mentions, the activity and audit log that earlier tasks logged as structured `Log::info` events until now, and attachments with their files. Each of them carries private-project content into new places (lists, downloads, feeds, exports, stored files), so each follows the existing rules: everything is reached through AccessibleProjects/AccessibleTasks, a hidden project is a 404, a 403 only concerns what the caller can already see, every writer locks team → project → task and re-checks on the locked rows, every key into teams and projects cascades for the trash purge. CORE-009 (notifications) builds on the mentions; CORE-006 leaves room in task detail for the UI, which is not part of this task. This ADR settles what the specs leave open, taking the most conservative option where they are silent.

## Decisions

### 1. Endpoints and rights

All under the `auth` group of `/api/v1`. `{task}` resolves through AccessibleTasks, `{project}` through AccessibleProjects, `{attachment}` through the new AccessibleAttachments (§5), so a hidden, trashed, foreign, random or malformed ID is the same 404 everywhere.

| Endpoint | Who | Notes |
|---|---|---|
| `GET /tasks/{task}/comments` | anyone who can see the project | newest first |
| `POST /tasks/{task}/comments` | `contribute` | `201` |
| `PATCH /tasks/{task}/comments/{comment}` | the author, while they may `contribute` | `200` |
| `DELETE /tasks/{task}/comments/{comment}` | the author (while they may `contribute`), or a moderator | `204` |
| `GET /tasks/{task}/attachments` | anyone who can see the project | metadata, newest first |
| `POST /tasks/{task}/attachments` | `contribute` | multipart; `Idempotency-Key`; `throttle:attachment-uploads`; `201` |
| `GET /attachments/{attachment}/download` | anyone who can see the project | streamed |
| `DELETE /attachments/{attachment}` | the uploader (while they may `contribute`), or a moderator | `204` |
| `GET /tasks/{task}/activity`, `GET /projects/{project}/activity` | anyone who can see the project | newest first |
| `GET /me/activity` | authenticated | own entries only (§4) |

- **Moderators** ("Owner/Project Manager", API_SPEC §6.2 and §6.3) are `ProjectPolicy::moderate`, the `manageMembers` rule used for labels and the workflow: the Team Owner, or a Team Admin or Member with the `manager` role. A Team Admin without it moderates nothing, a Team Viewer never (DECIDED-003). `App\Domain\Collaboration\AuthoredContent` holds the author/moderator rule for comments and attachments.
- **"Edit own comment — Author; project write permission"** is read literally: only the author edits, and only while they may still write in the project. A moderator may delete a comment but never rewrite someone else's words. An author demoted to Team Viewer, or removed from a private project, can no longer edit or delete their own comment (403, or 404 once the project is hidden).
- **Order of checks:** FormRequests authorise before they validate, so a caller without the right gets 403 whatever the body (AUTH-04). A `{comment}` that is not a live comment of the route's task is a 404 before the right is checked.
- **Archived and trashed:** every write answers 423 on an archived team or project (reads and downloads keep working) and 404 on a trashed project or task. `LockRecheck`-style tests cover every writer against a demotion (409) and against the project becoming invisible (404) after the request was authorised.

### 2. Comments and mentions

- **Schema (`2026_10_21_000200`):** `task_comments` as in DATABASE.md §5 plus `team_id` and `project_id` (§10.1: descendants carry them for scoping and composite keys; technical addition), with `(task_id, project_id) → tasks` and `(project_id, team_id) → projects` cascading, `author_user_id → users` RESTRICT, a non-blank body of at most 10,000 characters (CHECK), `edited_at >= created_at`, and the list index `(task_id, created_at DESC, id DESC)`.
- **Body:** Markdown source, 1–10,000 characters (`required`, `string`, `max`; blank is `required`), stored and returned as written; clients sanitise on rendering (API_SPEC §6.1). Any other field is `unknown_field`.
- **Not versioned, no Idempotency-Key.** §1.4 lists neither comments among the versioned resources nor comment creation among the idempotent creates, so there is no `If-Match` and no key; the row locks serialise edits (the last one wins). A retried POST can create a second comment; that is the specified contract.
- **Edits** set `edited_at` and record `comment.edited` (§6.2 "Comment edits keep edit timestamp and audit record"). The previous text is not kept anywhere: the audit record says *that* and *when* the comment changed, not what it said. Re-sending the same body is a no-op.
- **Deletes** are soft (`deleted_at`): the comment disappears from every read path at once, its mentions are removed, and the activity log keeps only a `comment.deleted` tombstone with the comment ID and whether a moderator deleted it (§6.2 "tombstones … without exposing content"). DATABASE.md §5 ties comment soft-deletion to the 30-day recovery policy; there is no restore endpoint, so the row is kept for 30 days (`TrashRetention`) and then hard-deleted by the daily `model:prune` (`TaskComment::prunable()`).
- **List order** is §1.4's default, `created_at desc, id desc`; no other sort is offered (none is allowlisted for this endpoint).
- **Mentions (API_SPEC §6.2 "explicit server-validated eligible users, not arbitrary free-text matches"):**
  - The token is `@` followed by a user UUID (`@018f8c70-…`), which a client inserts when someone picks a person. Names are never matched (`@Sara` is text); the token must not follow a letter, digit, `_` or `@` (an e-mail address is no mention) nor run on into more letters, digits, `_` or `-`. At most 50 distinct candidates per comment are considered; the pattern is linear.
  - **Eligible** is "can see the project now" (`ProjectPolicy::view`): an enabled member of the project's team, and for a private project the Team Owner or an explicit member. A Team Viewer can be mentioned (they can read the comment). Everyone else (another team's user, a non-member Admin, a disabled account, a random ID) stays plain text, with the identical response, so the endpoint is no probe for accounts. The resolved users come back as `mention_user_ids`; the caller can already list the project's and team's members, so this discloses nothing new.
  - Stored in `task_comment_mentions` (PK `(comment_id, user_id)`, index `(user_id, created_at DESC)`), a technical addition: CORE-009 needs them. Edits re-resolve the body: removed mentions go, new ones are added.
  - **Hook for CORE-009:** `App\Domain\Comments\Events\UsersMentioned` (comment, task, project and team IDs, actor, newly mentioned user IDs) implements `ShouldDispatchAfterCommit`, so it never fires for a request that rolls back. Nothing listens yet. A listener must re-resolve everything and re-check access at send time (API_SPEC §9, FR-COL-005).

### 3. The activity and audit log

- **One table, three levels (technical correction of DATABASE.md §5).** `task_activities` (`2026_10_21_000220`) holds **task** entries (`task_id` and `project_id`), **project** entries (`project_id` only: creation, visibility, membership) and **team** entries (neither: role changes, removals, ownership transfers). NFR-SEC-005 and ARCHITECTURE.md §11.2 require the last two to be audited, and BRD §10 names a conceptual `audit_events`; one table keeps one append-only mechanism and one authorization rule per level. `project_id` and `task_id` are therefore nullable, with `CHECK (task_id IS NULL OR project_id IS NOT NULL)`.
- **Keys:** `team_id → teams`, `(project_id, team_id) → projects(id, team_id)` and `(task_id, project_id) → tasks(id, project_id)` cascade (ADR-022 §5), so an entry can only name its own project and team, and the purge removes it with them; `actor_user_id → users` SET NULL. Indexes `(task_id|project_id|team_id|actor_user_id, created_at DESC, id DESC)` serve the feeds and DATABASE.md §5/§12.
- **Append-only in the database:** a trigger refuses UPDATE, DELETE and TRUNCATE issued directly (`task_activities is append-only`). Foreign-key actions pass (the purge's cascades, the SET NULL of a deleted user): they run inside the referential trigger, which the guard recognises by `pg_trigger_depth() > 1`. The application never updates an entry.
- **Bounded, sanitised `changes` (DATABASE.md §5).** `App\Domain\Activity\Activity` declares every action and the keys it may carry; values are IDs, enum values, dates, counts, booleans, field-name lists or `{from, to}` pairs of those, at most 64 characters each. Anything else is a `LogicException`, and the database refuses a non-object or anything over 4 KiB. Titles, descriptions, comment bodies, checklist text, label names and file names are never copied: `task.updated` lists the changed field names and gives `from`/`to` only for `status_id`, `assignee_user_id`, `parent_task_id`, `priority` and `due_date`.
- **Same transaction as the change** (ARCHITECTURE.md §7, DATABASE.md §11 "insert task and activity atomically"): a refused, stale (412, API_SPEC §14.3) or no-op change records nothing.
- **What replaces the structured audit logs (ADR-018 §7, ADR-020 §9, ADR-023 §10).** Where the specs ask for an audit or activity record, the `Log::info` event is replaced by an activity entry:

  | Former log event | Activity action | Level |
  |---|---|---|
  | `task.created`, `task.updated` (with `task.status_changed`, `task.assignee_changed`), `task.trashed`, `task.restored_from_trash` | `task.created`, `task.updated`, `task.trashed`, `task.restored` | task (FR-COL-002, FR-TASK-006, ARCHITECTURE §7) |
  | `task.checklist_item_created/updated/deleted` | same names | task (significant task changes) |
  | `task.assignments_released` (one summary line) | `task.assignee_released`, one entry per task, `source: system`, `from` and `reason` | task (ADR-023 §5) |
  | `project.created`, `project.visibility_changed`, `project.member_added/role_changed/removed` | same names | project (NFR-SEC-005) |
  | `team.member_role_changed`, `team.member_removed`, `team.ownership_transferred` | same names | team (NFR-SEC-005, DATABASE §11) |
  | `team.invitation_accepted` (CORE-002) | `team.member_added` (actor: the joining user; `user_id`, `role`, `invitation_id`) | team (every membership is audited, NFR-SEC-005) |
  | `team.invitation_created`, `team.invitation_revoked` (CORE-002) | same names (`invitation_id`, `type`, `role`; never the address or the token) | team |
  | `team.invitations_revoked` (CORE-002, an issuer lost the right) | same name, `source: system`, actor NULL (`issuer_id`, `reason`, `count`) | team |

  New: `comment.created/edited/deleted`, `attachment.added/removed`. Operational events stay logs: archive, trash, restore and purge of teams and projects, workflow and label configuration, project settings, exports, key conflicts and purge failures. They are not required as audit records by the specs, and `trash.*` must outlive the rows it describes. `team.member_removed` no longer carries the count of revoked project memberships: a team entry must not hint at private projects.
- **Assignment releases** are set-based (`Activity::forTasksSql`): one `INSERT … SELECT` with the same predicate as the release's `UPDATE`, under the same locks, using `sn3_uuid_v7()` (a SQL function added by the migration, the expression CORE-004's seed used inline). The actor is NULL (`source: system`): the release is a consequence of someone else's membership change, which has its own entry.

### 4. Reading activity

`App\Domain\Activity\ActivityFeed`, cursor-paginated, newest first (`created_at desc, id desc`), always authorization-scoped before ordering and paging:

- **Task timeline** (`/tasks/{task}/activity`): the task's entries, for anyone who can see the task.
- **Project timeline** (`/projects/{project}/activity`): the project's own entries and those of its tasks (trashed tasks included: entries hold IDs only), for anyone who can see the project. Private-project activity therefore reaches only its members and the Team Owner, and is a 404 for everyone else.
- **Own activity** (`/me/activity`, API_SPEC §9 "Own authorized recent activity"): read as the caller's own entries (`actor_user_id`), and only where they may still see them now: project and task entries of projects AccessibleProjects grants them, team entries of teams they still belong to. Someone removed from a private project or a team stops seeing their own entries there. It never lists anybody else's actions.
- **No team-wide feed.** API_SPEC defines none, so team entries and private-project entries cannot leak through a broader list; team entries are readable only by their actor and in the Owner's export.
- Representation: `id`, `team_id`, `project_id`, `task_id`, `actor_user_id`, `action`, `changes` (always a JSON object), `source` (`user`, `system`; `integration` is reserved for GitHub), `created_at`.

### 5. Attachments

- **Schema (`2026_10_21_000210`):** `task_attachments` as in DATABASE.md §5: keys into tasks and projects cascade, `uploaded_by → users` RESTRICT, `storage_key` unique and CHECKed against `objects/<team>/<project>/<32 hex>`, `original_name` 1–255 characters, `sha256` 32 bytes, `size_bytes >= 0`. No `updated_at` (§5 lists none; attachments are immutable). `deleted_at` marks a removal in progress (below). Indexes: the list `(task_id, created_at DESC, id DESC)`, the quota sum `(team_id) INCLUDE (size_bytes) WHERE deleted_at IS NULL`, pending removals.
- **Storage (API_SPEC §6.3 "never use public storage", ARCHITECTURE §5.3):** a dedicated private disk, `attachments` (`storage/app/attachments`, `serve => false`, outside the served `local` root; `SN3_ATTACHMENTS_DISK` may name a private S3 disk on Cloud). Each row keeps the disk it was written to (`storage_disk`), so switching `SN3_ATTACHMENTS_DISK` needs no migration: downloads read each file from its own disk, and the purge and the sweep clean **every disk attachments may be on**: the configured one, every disk a row still names, and the previous disks the operator lists in `SN3_ATTACHMENTS_PREVIOUS_DISKS` (needed only for a disk no row names any more). Keys are `objects/<team_id>/<project_id>/<128 random bits in hex>`: opaque, random (not the time-ordered attachment ID), never derived from the file name, and grouped by team and project so a purge can delete by prefix. The disk, the key and the raw digest never appear in a response.
- **Downloads are streamed through the authorized route**, re-resolved on every request (AccessibleAttachments: a live attachment of a live task of a project the caller can see now). There is no public URL and no signed storage URL, so a removed member's next download is a 404 (AUTH-05, DB-T08) and revoked access cannot be replayed. Headers: the stored (sniffed) `Content-Type`, `Content-Length`, `Content-Disposition: attachment` with an ASCII fallback and an RFC 5987 UTF-8 name, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, `Cross-Origin-Resource-Policy: same-origin`, `Cache-Control: no-store, private`. A visible attachment whose file cannot be read (missing, or the storage is down) answers **`503 service_unavailable`** and logs `attachment.file_missing` as an **error** (IDs and the disk only): it is an integrity problem for the operator, and the client may retry; 410 stays reserved for expired invitations and integration state (§1.3).
- **Size and quota (DECIDED-004, LIM-01, LIM-02):** `sn3.attachments.max_bytes` (25 MiB) per file and `sn3.attachments.team_quota_bytes` (2 GiB) per team, both configurable for self-hosted instances (`0` = no limit; the features never change). Both answer **413 `payload_too_large`** (§1.3 "Attachment/body exceeds configured limit"). The file size is measured on the received file, never taken from the client; a file PHP refused for its size (`UPLOAD_ERR_INI_SIZE`), and a body over `post_max_size`, are 413 too. The PHP limits in `deploy/docker/php/sn3.ini` are 26M/27M, just above the cap. The quota counts every live attachment row of the team in every project, trashed tasks and projects included (their files are still stored until the purge); a removal frees its space at once.
- **The quota is a side channel (residual, accepted).** The quota is per team (DECIDED-004), so a 413 tells a project writer that the team's stored attachments, private projects' files included, are near the limit. It reveals nothing else: no project, name, count or size is answered, there is no usage endpoint, the 413 envelope is the generic one also used for the per-file cap, and uploads are rate-limited (20/minute per user), so probing for changes in usage is slow and coarse. Per-project quotas would remove it, but the decision register fixes a team quota; a usage view for the Team Owner (who sees every project) is a possible follow-up.
- **Quota races:** the quota is checked before anything is written (a team already at its quota stores nothing) and again under the team row lock, which every attachment writer of the team takes first, so concurrent uploads cannot overshoot it together. The file itself is written between the two checks, outside the locks, so a slow store does not hold the team's write lock; a request that then fails deletes its file in the same request (on its own rollback and on the surrounding `idempotent` transaction's, `DB::afterRollBack`). A real-process race test shows that two uploads that each fit but not together end with one row, one file and one 413.
- **Types (API_SPEC §6.3 "Validate actual MIME/file signature where feasible"):** the specs give no list, so this is an allowlist (`App\Domain\Attachments\AttachmentTypes`) of common document, image, media and archive formats: PNG, JPEG, GIF, WebP, HEIC/HEIF, PDF, plain text (including Markdown, CSV, TSV, logs), JSON, zip and the zip-based Office Open XML and OpenDocument files, gzip, tar, MP4, QuickTime, WebM, MP3, Ogg, WAV.
  - The type is **sniffed from the content** with libmagic (`finfo`); the client's `Content-Type` is ignored, and the sniffed type is what is stored and served.
  - The file name's extension must be one listed for the sniffed type, so a Windows executable named `cat.png`, a PDF named `run.exe`, `report.pdf.exe` and an HTML page named `notes.txt` are all refused with **422 `mimetypes`**. HTML, SVG, XML, scripts, executables, unknown binaries, legacy Office (OLE) files and anything libmagic cannot identify are never accepted; an empty file is `min`.
  - **Polyglots** (a GIF that is also JavaScript, a PDF with a zip appended) are accepted as what they sniff as: they *are* valid files of that type. They are harmless because no download is ever rendered or run inline (`attachment`, `nosniff`, sandbox CSP). **Archives** are stored as they are and never unpacked on the server, so archive bombs cost nothing; the server does not inspect archive members.
  - Malware scanning is allowed to be asynchronous by §6.3 and is not part of this task (no quarantine state yet).
- **File names (§6.3 "original filename is metadata only"):** `AttachmentFilename` keeps the last path segment for `/` and `\`, removes control characters, NUL, line and paragraph separators (`\p{Zl}`, `\p{Zp}`), the zero-width space (U+200B), the byte-order mark and the bidirectional overrides and isolates (an RLO cannot make `invoice‮fdp.exe` look like a PDF; important in an Arabic-first product), keeps the zero-width joiner and non-joiner (Arabic and Persian names need them), normalises to NFC, trims spaces and dots at both ends (so `.env.txt` becomes `env.txt`), caps at 255 characters keeping the extension, and falls back to `file`. The name never becomes a path.
- **Idempotency (§1.4 "attachment initiation"):** `POST` requires `Idempotency-Key` (400 without). The `idempotent` middleware's payload digest now includes each uploaded file's client name, size and content SHA-256 (an additive change: requests without files hash exactly as before), so the same key with another file is `409 idempotency_key_reused`, never a replay of the first upload. A replay returns the original `201`, body and `Location`, and stores nothing. The idempotency record now also takes the team from a `{task}` route, so it goes with the team.
- **Rate limit (§1.4 "separate stricter limits for … uploads"):** `attachment-uploads`, 20 per user per minute (`SN3_RATE_LIMIT_ATTACHMENT_UPLOADS_PER_MINUTE`, `0` disables it on self-hosted instances), on top of the global 120/minute; `429 rate_limited` with `Retry-After`.
- **Representation:** `id`, `task_id`, `uploaded_by`, `filename`, `mime_type`, `size_bytes`, `sha256` (hex), `download_url` (the authorized route, not a storage URL), `created_at`.
- **Deleting an attachment** marks the row `deleted_at` together with the `attachment.removed` entry (it is gone from every read path and out of the quota at once); after commit the file is deleted and then the row. If the storage fails, the marked row stays and the sweeper finishes it.
- **Files and the trash purge (ADR-022 §5 follow-up):** `PurgeTrash` now dispatches `ProjectPurged` and `TeamPurged` after each committed delete (a two-line, additive change). `DeletePurgedAttachmentFiles` deletes the purged project's or team's key prefix; a storage failure is logged and left to the sweeper. Recovering a project or team within the 30 days brings its files back untouched, since nothing is deleted before the purge.
- **`attachments:sweep` (hourly at :35):** on every disk attachments may be on, finishes pending removals, deletes `objects/<team>/` and `objects/<team>/<project>/` prefixes whose team or project row no longer exists, and deletes files under `objects/` that no row of that disk references and that are older than an hour (uploads whose process died between write and rollback). It walks each disk with a lazy Flysystem listing and checks keys against the database in batches of 500, so memory does not grow with the number of files. It only ever considers keys matching the storage-key pattern.
- **Jobs:** none are added. Everything above runs in the request or in the purge, which already re-resolve their rows (ADR-022 "jobs re-resolve their project"); CORE-009's mention notifications will be the first project-scoped jobs.

### 6. Limits and parity

Cloud and self-hosted instances run the same code; only the configured limits differ (`SN3_ATTACHMENTS_MAX_BYTES`, `SN3_ATTACHMENTS_TEAM_QUOTA_BYTES`, `SN3_RATE_LIMIT_ATTACHMENT_UPLOADS_PER_MINUTE`, `SN3_ATTACHMENTS_DISK`; docs/SELF_HOSTING.md). Comments have no rate limit of their own (none is asked for) beyond the global one; the 10,000-character cap and the 50-mention bound keep each request small.

### 7. Team export (ADR-024 §2 and §8 follow-ups)

- **Three new sections, still `format_version` 1** (additive):
  - `comments`: `id`, `task_id`, `author_user_id`, `body`, `mention_user_ids`, `edited_at`, `created_at`, `updated_at`; live comments of exported, live tasks.
  - `activity`: `id`, `project_id`, `task_id`, `actor_user_id`, `action`, `changes`, `source`, `created_at`; the team's own entries and those of the exported projects, except entries of tasks in the task trash (DATABASE.md §13 "audit metadata").
  - `attachments`: `id`, `task_id`, `uploaded_by`, `filename`, `mime_type`, `size_bytes`, `sha256`, `file`, `created_at`; live attachments of exported, live tasks.

  Each is scoped through `TeamExportContext::projectIds()` with an explicit field allowlist, like every section; a context for a non-Owner holds nothing of a private project they cannot see.
- **The files are in the archive** (decision recorded as asked): API_SPEC §13 says exports "include … authorized attachments", DATABASE.md §13 "attachment manifests and signed downloadable attachment archive", and ADR-024 §8 "the binary files under `files/` in the same archive". Each attachment's file is the entry `files/<attachment_id>` (never its name, so nothing in an export can traverse or collide), named by the record's `file`, with the record's `sha256` to check it against. A file the storage cannot find is exported as `file: null` instead of failing the export.
- **Streaming zip writer.** As ADR-024 §8 asked, `TeamExportWriter` no longer builds the archive with PharData, which rewrote the whole archive to compress it. `App\Domain\Exports\ZipStreamWriter` streams each entry once, with flat memory: JSON deflated (zlib, bundled with PHP), attachment files stored as they are. ZipArchive (with `CHECKCONS`), Python's `zipfile` and `unzip -t` accept its archives.
- **ZIP64 (APPNOTE 4.5), so neither size nor entry count limits an export.** An entry declared at or above 3.75 GiB (or of unknown size) gets ZIP64 size fields in its local and central headers; an entry starting at or beyond that offset gets its offset in the central header's ZIP64 field; 65,535 or more entries, or a central directory beyond that offset, add the ZIP64 end-of-central-directory record and locator. Smaller archives stay plain zip 2.0, as before. Data files and attachments pass their known sizes. Tested: 70,000 entries, and every ZIP64 structure with a lowered threshold (ZipArchive `CHECKCONS`). Checked by hand: a real 4.3 GB archive (an entry of 4 GiB + 12,345 bytes followed by a small one at an offset beyond 4 GiB) read back by ZipArchive, Python's `zipfile` and `unzip -l`.
- **Measured** (`TeamExportWriter::build`, local disks, a 2-vCPU development container, PostgreSQL 16 on the same host): 10,000 tasks with 30,000 comments, 50,000 activity entries and 200 attachments of 1 MiB built in **7.4 s** (203 MB archive); the same with 1,000 attachments of 2 MiB, a team at its full 2 GiB quota, in **11.4 s** (2.0 GB archive). Peak memory stayed at 55–57 MB. The job keeps the worker's 60-second timeout on local storage; the work directory and the export disk need free space for an archive as large as the team's attachments.

## Consequences and follow-ups

- **CORE-009** listens to `UsersMentioned`, re-checks access at send time, and adds notification rows that cascade with their team or project. Comment notifications for watchers can use the `comment.*` entries.
- **CORE-006** shows comments, attachments and the activity timeline in task detail (rendering `@<user-id>` as names, sanitising Markdown), in Arabic and English; upload errors map 413/422 `mimetypes` to translated messages.
- **Cloud on S3:** exports of large teams stream every file from the bucket within the job; before attachments live on S3, measure there and, if needed, give `BuildTeamExport` its own queue with a longer timeout and matching `retry_after` (ADR-024 §8). Lifecycle rules must not expire `objects/` keys.
- **Asynchronous malware scanning** with a quarantine state that blocks downloads (§6.3 "may").
- **GitHub (GH-\*)** records integration-originated changes with `source: integration`.

## Open product questions (implemented conservatively)

1. Should `/me/activity` show the caller's own actions (implemented) or everything that happened in their projects?
2. Should moderators be able to edit other people's comments? Implemented: no, delete only.
3. Should legacy Office files (`.doc`, `.xls`, `.ppt`), SVG or other types be accepted, and should operators be able to extend the list? Implemented: a fixed allowlist without them.
4. Should a project trashed to free space count against the team quota until it is purged? Implemented: yes, its files are still stored.
5. Should deleted comments be recoverable (there is no restore endpoint)? Implemented: kept 30 days, then pruned; not restorable through the API.
6. Should very short text files that libmagic cannot classify (a single character) be accepted? Implemented: refused as an unknown type.

# ADR-017 — Teams, tenant scoping, idempotency and versioned updates

- **Status:** Accepted
- **Date:** 2026-10-16
- **Task:** FND-005 (#6)
- **Decision inputs:** DATABASE.md §1, §3, §10, §11, §14, §20; API_SPEC.md §0.4–0.5, §1.1–1.4, §2, §3; ARCHITECTURE.md §4, §5; DEVELOPMENT_PLAN.md §14; BRD FR-AUTH-003

## Context

FND-005 lays the tenancy foundation every later feature builds on: UUIDv7 identifiers, teams and memberships with an enforced single Owner, policies, a scoped way to resolve team-owned data, and the API mechanisms DEVELOPMENT_PLAN §14 requires before any versioned endpoint exists (version fields with `If-Match`, `Idempotency-Key` records). Team mutations (create, rename, roles, transfer, archive, delete) are CORE-001; invitations are CORE-002.

## Decisions

### 1. Identifiers
Every domain table uses a `uuid` primary key generated by the application with Laravel 12's `HasUuids`, which produces **UUIDv7** (time-ordered, so B-tree inserts stay local and `id` is a stable pagination tie-breaker). An architecture test requires `HasUuids` on every model in `App\Models` (`UserPreference` is keyed by `user_id`).

### 2. `teams` and `team_memberships` (migration group 01)
Columns follow DATABASE.md §3 and §20 (`deleted_at` for the 30-day trash, independent `archived_at`). Additions:

- `teams.slug` has a CHECK for API_SPEC §3's format `[a-z0-9-]{3,40}` and stays unique deployment-wide, including teams in the trash.
- `team_memberships.role` is `text` with a CHECK (`owner|admin|member|viewer`), not a database enum.
- Deleting a team cascades to its memberships (only the trash purge does that); deleting a user who still has memberships, or owns a team, is refused (`RESTRICT`).

API_SPEC §3 also lists `description` and an avatar for teams. DATABASE.md §3 does not, so they are not added here; CORE-001, which implements `PATCH /teams/{team_id}`, adds them with an expand-only migration.

### 3. One Owner, enforced by PostgreSQL
DATABASE.md §3 requires exactly one `owner` membership per team, belonging to `teams.owner_user_id`, and suggests a deferrable trigger for strict enforcement.

- A partial unique index (`team_id WHERE role = 'owner'`) makes a second owner membership impossible at any moment.
- Two **deferred constraint triggers** (on `teams` and on `team_memberships`) call `sn3_assert_team_owner()` at COMMIT and raise `check_violation` unless the team's only owner membership belongs to `owner_user_id`. Inside one transaction the ownership transfer (CORE-001) may update the team and both memberships in any order; it can never commit a team without its matching Owner, remove or demote the Owner, or move the Owner's membership elsewhere.

The application keeps doing the right thing first (row locks, single transaction, audit). The triggers are the backstop. Tests force the deferred checks with `SET CONSTRAINTS ALL IMMEDIATE`, because each test runs in a transaction that never commits.

### 4. Tenant scoping: `AccessibleTeams` and route binding
`App\Support\Tenancy\AccessibleTeams` is the only way to reach a team for a user: teams where the user has a membership, soft-deleted teams excluded, with the user's own membership eager-loaded (so policy checks cost no query). `{team}` route parameters are bound through it (`TenancyServiceProvider`). A non-member's team, a trashed team, a random UUID and a malformed ID (validated before it reaches PostgreSQL, where comparing a non-UUID with a `uuid` column is an error) all produce the same 404 `not_found`, with no name or ID echoed (ARCHITECTURE §5.2 steps 1–3, API_SPEC §0.4).

**Pattern for later resources:** resolve the team first, then reach children through its relations (`$team->projects()->whereKey($id)->firstOrFail()`, Laravel scoped bindings). Never `Model::find($id)` with a later policy check. Private-project rules (DECIDED-003) layer on top of this in CORE-003.

### 5. Policies
`TeamPolicy` encodes API_SPEC §3's permission column: members `view`; Owner/Admin `update`, `invite` and `createProject`; Owner-only `changeMemberRole` (never the Owner's own role), `transferOwnership`, `archive`, `delete`, `restore` (from the trash) and `export`. Anyone except the Owner may leave (`removeMember` on oneself), and only the Owner removes others. *(Superseded in part by ADR-018 §6: the policy now lets the Owner through and `RemoveMember` refuses with 409.)* Non-members are denied everything. Resource-state rules (archived teams are read-only → 423) and role-grant limits belong to the CORE actions.

### 6. Read endpoints and pagination
`GET /api/v1/me/teams` (API_SPEC §2) and `GET /api/v1/teams` (§3) return the same list: the caller's teams with their own `role`, newest first (`created_at desc, id desc`). `GET /api/v1/teams/{team}` returns one. This is what the team switcher uses (FR-AUTH-003). The active team itself is UI context, not authorization (ARCHITECTURE §5.1), so nothing is stored server-side.

`App\Http\Pagination\CursorPagination` implements §1.1/§1.4 for every list: `limit` 1–100 (default 25, otherwise 422), and an opaque `cursor` = base64url(JSON of Laravel's cursor, expiry, endpoint path) + HMAC-SHA256 keyed from `APP_KEY`. A tampered, expired (24 h), malformed or other-endpoint cursor is 400 `bad_request`. The cursor only carries the position; the query stays authorization-scoped. Rotating `APP_KEY` invalidates outstanding cursors, which is harmless.

### 7. `Idempotency-Key` (`api_idempotency_records`, middleware alias `idempotent`)
Table as in DATABASE.md §20. `route_key` is the method and path (`POST /api/v1/teams/{uuid}/invitations`), so the unique `(actor_user_id, route_key, idempotency_key)` also scopes by tenant and parent resource. `team_id` is filled from the bound team for clean-up.

- Missing or non-UUID key: 400 `bad_request` (API_SPEC does not name a code; this follows the IETF Idempotency-Key draft).
- The request runs in **one transaction** holding `pg_advisory_xact_lock` on the scope. A concurrent duplicate waits, then replays the committed result. It never runs twice, and a crash leaves no half-stored key.
- Only successful (2xx) results are stored (a body-less 204 replays as 204). Any other outcome rolls the whole request back and leaves the key unused, so the client can fix the request and retry with the same key. Consequently, nothing an idempotent route writes survives a non-2xx answer.
- Same key and canonical payload (query and body, key order ignored): the stored status and body are replayed with `Idempotent-Replayed: true`. A different payload: 409 `idempotency_key_reused`, nothing runs. After 24 hours the key is new again, and `model:prune` removes expired rows daily at 03:30.
- Routes list `auth` and route throttles before `idempotent`. Jobs dispatched inside should use `->afterCommit()` so non-database queues cannot run them before the commit.

### 8. Versions and `If-Match`
The versioned tables (projects, tasks, sprints, statuses, issue mappings) do not exist yet, so FND-005 provides the mechanism: `App\Http\Concurrency\IfMatch::version()` (missing header → 428 `precondition_required`; anything but `"<positive integer>"` → 412 `version_mismatch`), and `App\Support\Concurrency\OptimisticLock::update()`. That method locks the row (`SELECT … FOR UPDATE`), compares `version`, applies the change and saves with `version + 1` in one transaction, raising `StaleVersionException` (rendered 412) on mismatch. A no-op change keeps the version. Each versioned table adds `version bigint NOT NULL DEFAULT 1` and an integer cast.

### 9. `citext` emails
DATABASE.md §20 makes `citext` the only option for case-insensitive emails. FND-004 had shipped `varchar` plus a unique `lower(email)` index (allowed by §3). An expand-only migration switches `users.email` to `citext` with its existing unique index and drops the redundant `lower()` index. `citext` is a trusted extension (PostgreSQL 13+), so the database owner can create it without superuser rights. The application still normalises emails.

## Consequences

- CORE-001/002 add mutations on top of `AccessibleTeams`, `TeamPolicy`, `idempotent` and the owner triggers. CORE-001 adds the concurrent ownership-transfer test (DB-T06) with real parallel connections.
- Restoring a trashed team (CORE-010) needs an Owner-only resolver variant that includes trashed teams, because `AccessibleTeams` hides them.
- The partial index and triggers are PostgreSQL-specific, consistent with PostgreSQL being the only supported engine.
